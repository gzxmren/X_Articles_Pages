一篇文章讲清楚 Prompt、Context、Harness、Loop 的区别
1,322
最近 AI Agent 圈里又多了一个热词（老词热炒）：
Loop Engineering。
如果你过去半年一直在用 Claude Code、Codex、Cursor、Cline 这类工具，大概率已经刷到过类似说法：
你应该设计一个 Loop，然后让 Loop 去提示 agent。
有人理解成：Prompt Engineering 过时了。
有人理解成：让 AI 一直循环跑就行。
也有人觉得这只是：cron job 套了个新名字
我重新看了一圈资料后，觉得这几个判断都不够准确。
Loop 是让系统负责触发、上下文、验证、状态、停止和交接。
过去你是那个不断提示 AI 的人。
现在你要设计一个系统，让这个系统在合适的时候提示 AI，并判断下一步该继续、重试、停止，还是交给人。
这是 Loop Engineering 真正值得讨论的地方。
先把四个词拆开
现在 AI 工程里经常被放在一起讲的四个词是：
Prompt Engineering、Context Engineering、Harness Engineering、Loop Engineering。
四层问题。
Prompt Engineering：这一轮怎么说。
你要把任务讲清楚，把输出格式讲清楚，把限制条件讲清楚。
它解决的是：一次调用里，如何减少误解
Context Engineering：这一轮给 AI 看什么。
代码库太大、资料太散、历史信息太多，AI 不可能天然知道哪些重要。
Context Engineering 解决的是：如何筛选、组织、压缩和注入上下文
Harness Engineering：AI 怎么安全行动。
一个裸模型只会生成文本。
它能读文件、改代码、跑测试、开浏览器、接数据库、受权限和沙箱约束，是因为外面有 Harness。
OpenAI、Anthropic、Martin Fowler 的文章里都反复强调过：真正让 coding agent 能干活的，不只是模型，而是模型外面的工具、权限、状态、日志、检查和恢复路径。
Loop Engineering：系统怎么持续推动 AI 干活。
它回答的是：任务什么时候启动？每轮给 AI 什么上下文？结果怎么验证？失败怎么进入下一轮？状态写在哪里？什么时候必须停止？什么情况交给人？
Prompt 是一次指令。Context 是输入材料。Harness 是执行底座。Loop 是外层闭环。
为什么 Loop 不是新发明
Loop Engineering 没有发明 循环
早在 2022 年，ReAct 就已经把 LLM 放进了 推理、行动、观察 的交替过程里：模型不只是想，也会行动；行动拿到外部环境反馈后，再继续调整下一步。
2023 年的 Self-Refine 研究的是 先生成、再反馈、再改写 的迭代改进。
Reflexion 则让语言智能体把失败反馈写成文字记忆，下一轮再读这些经验继续尝试。
Anthropic 在 Building Effective Agents 里讲 Evaluator-Optimizer 工作流，本质也是一个生成者产出，一个评价者给反馈，然后继续优化。
所以如果有人把 Loop Engineering 说成：AI 第一次会循环了，那不严谨。
真正的新意不在循环二字，而在循环的边界变了。
以前的循环多发生在一次 agent 执行内部：
reason -> act -> observe -> reason again
现在讨论的 Loop，是把这个循环放大到真实工作系统里：
trigger -> assemble context -> call agent -> execute tools -> collect evidence -> verify -> update state -> retry / stop / handoff
这就不只是模型策略了，而是工程系统设计。
Harness 和 Loop 最容易混
Claude Code、Codex 这类工具，本身已经提供了很强的 Harness：
  • 能读取代码库和文档。
  • 能编辑文件。
  • 能运行命令、测试和脚本。
  • 能接 MCP、浏览器、GitHub、Slack、Linear 等外部系统。
  • 能用权限、审批、沙箱限制行动范围。
  • 能记录轨迹、diff、日志和运行结果。
Agent 能不能行动？它能碰什么？出事后能不能追踪？
这就是 Harness。
但你平时基于这些工具做的很多自动化，并不是在重新造 Harness。
比如：
  • CI 失败后自动读取日志、修一个最小问题、重新跑测试。
  • 每天早上汇总 GitHub issue、挑出需要处理的 bug。
  • 每周检索竞品动态，生成一份有链接和日期的更新。
  • 写完文章后自动检查事实来源、标题、插图、分发文案。
  • 把会议纪要拆成任务、知识卡片和待确认问题。
这些更接近 Loop。
Harness 让 AI 有手有脚。Loop 让 AI 有节奏、有验收、有刹车。
一个真正的 Loop 至少要有 7 个部件
很多人说自己做了 Loop，其实只是让 AI 多跑几轮。
多跑几轮不是闭环。闭环至少要有这 7 个部件。
1. Goal：目标
让 auth 相关测试全部通过，并且不引入新的 lint/type error
目标越像一句愿望，Loop 越容易发散。
目标越能被验证，Loop 越容易收敛。
2. Trigger：触发
什么时候启动？
是人手动说开始，还是 CI 失败触发？是每天 9 点触发，还是有新 issue、新邮件、新评论、新网页变化时触发？
没有触发条件，Loop 只是一次任务。
3. Context：上下文
每轮给 AI 看什么？
失败日志、当前 diff、项目规则、历史尝试、关联文件、业务背景、上一次运行状态，这些不能全靠 AI 猜。
Context 不是越多越好。越是长期任务，越要控制每一轮看到什么、忽略什么、从哪里恢复记忆。
4. Action：每轮动作
每一轮允许 AI 做什么？
只允许读日志和改测试？能不能改业务代码？能不能安装依赖？能不能访问网络？能不能提交 PR？能不能改数据库迁移？
Action 设计不清楚，AI 就会把小修做成大重构。
5. Verify：验证
这是 Loop 的心脏。
没有真实 Verify，就没有真实 Loop。
代码场景里，Verify 往往是测试、lint、type check、构建、截图回归、benchmark。 内容场景里，Verify 往往是来源数量、事实核查、结构清单、敏感词、引用回溯。 运营场景里，Verify 往往是链接可访问、日期正确、变更有证据、格式能导入。
最危险的 Verify 是：
AI 自己觉得完成了。
自评能作为辅助，但不能成为单独验收。
6. State：状态
Loop 必须知道上一轮发生了什么。
改了哪里？跑了什么命令？失败原因是什么？哪些方向试过了？下一轮先看哪里？
没有 State，AI 很容易在同一个坑里来回转。
Anthropic 的 long-running agent 文章里反复提到一个问题：长任务会跨多个上下文窗口，每个新 session 都像换了一个没交接的新工程师。
如果没有结构化交接材料，长期任务就会断。
7. Stop / Handoff：停止与交接
会停和会跑一样重要。
什么时候成功停止？ 什么时候预算耗尽停止？ 什么时候发现风险停止？ 什么时候必须交给人？
一个不会停的 Agent，不是自动化，是成本黑洞。
一个不会交接的 Agent，不是同事，是黑盒。
用 《自动修 CI》看一遍
普通 Prompt 是：
帮我修一下 CI。
AI 可能会改一堆文件，也可能只修表面错误，还可能在测试没跑完时宣布完成。
Loop Spec 应该长这样：
Goal 让当前 PR 的 CI 变绿，不改变无关代码行为。
Trigger GitHub Actions 中 auth、api、billing 任一 job 失败时触发。
Context 失败日志、PR diff、项目
AGENTS.md
、相关测试文件、最近一次成功提交。
Action 每轮只处理一个最可能失败原因；优先做最小修改；不做无关重构；涉及数据库迁移、权限、删除数据时停止。
Verify 对应测试通过；lint/type check 无新增错误；diff 不包含无关大改。
State 记录本轮判断、修改文件、运行命令、结果、下一轮建议。
Stop 验证通过就停止；最多 6 轮；超过 30 分钟停止；遇到权限/数据/安全风险交给人。
这里的Codex 或 Claude Code 能读文件、改代码、跑测试，是 Harness。 这份 Goal、Context、Verify、State、Stop，才是 Loop。
不止是代码，内容和知识库也需要 Loop
Loop Engineering 最早是在 coding agent 圈里火起来的，但它不只适用于代码。
内容生产 Loop
写一篇 2500 字公众号稿，包含 8 个公开来源、1 个核心判断、3 个案例、4 张配图提示词、1 段适合/不适合读者边界，并通过事实核查。
应该检查：
有没有来源？ 有没有把猜测写成事实？ 有没有夸大结论？ 图片中文字是否短到能渲染？ 是否保留了不确定性？
竞品监控 Loop
每周检索指定竞品的官网、博客、GitHub release、X/LinkedIn 公开动态，只记录产品、价格、渠道、招聘和文档变化，不写未经证实的市场判断。
验证标准是：
每条变化有链接、有日期、有截图或摘录，有 不确定/待确认 标记。
知识库整理 Loop
把新材料拆成 Source Unit、Knowledge Block、Topic Page，并更新索引，保证每个结论都能回到原文。
验证标准是：
索引可查、文件命名正确、双链有效、原文引用不丢、没有把原文没有的判断塞进知识块。
这些场景不同，但骨架一样：
目标明确。 上下文受控。 每轮动作有限。 验证真实。 状态可继承。 停止条件清楚。 异常能交给人。
为什么中文讨论里会有争议
中文社区里对 Loop Engineering 的讨论，大致分成两派。
一派觉得它是新阶段：AI 从 回答问题 走向 持续做事 ，人不再一轮轮推着 Agent 走，而是设计一个运行系统。
另一派觉得它是旧酒新瓶：ReAct、工作流、定时任务、自动重试、CI/CD、状态机早就存在，只是换了个更时髦的名字。
我觉得两边都对一半。
说它 不是新技术 ，对。
循环、状态、验证、重试、调度、权限、日志，这些都不是 2026 年才有。
说它 值得重新命名 ，也对。
因为 coding agent 的工作边界变了。过去很多闭环只能写在业务系统里，现在 agent 自己能读、写、查、跑、看结果，闭环能更贴近实际工作过程。
问题从 怎么写一句好 Prompt，变成了：
如何把 AI 放进一个可靠的生产流程里？ 如何让它持续推进，但不要失控？ 如何让它生成更多结果，同时不制造更多 Review 和维护负担？ 如何让组织知道它做了什么、为什么这么做、哪里还不确定？
AI 已经让个人写代码更快，但不代表组织交付天然更稳定。 Loop Engineering 真正要处理的，正是这个从个人效率到组织流程的断层。
三种 Loop，别混在一起
为了不把所有东西都叫 Loop，可以先拆成三层。
第一层：任务执行 Loop
关注当前任务怎么做完。
例子：修 CI、生成报告、补测试、整理资料。
核心问题是：每轮做什么，怎么验证，失败后怎么继续。
第二层：控制平面 Loop
关注任务怎么被管理。
例子：定时触发、工单分发、权限控制、预算限制、worktree 隔离、人工审批。
核心问题是：谁启动、谁授权、状态在哪、成本多少、风险怎么拦。
第三层：系统改进 Loop
关注这个 Loop 自己怎么变好。
例子：分析历史失败，发现 agent 老是漏跑 lint，于是更新 skill、hook 或 verifier；发现某类任务总是返工，于是修改上下文装配规则。
核心问题是：失败经验怎么沉淀进下一版系统，而不是永远靠人提醒。
很多团队卡住，是因为只做了第一层，甚至只做了“重复调用模型”，但没有第二层和第三层。
最短判断法
看到一个 Agent 系统，先问两个问题。
问题一：它是在增强 Agent 的行动边界吗？
比如增加工具、MCP、沙箱、权限、日志、文件系统、浏览器、hooks、subagents。
这是 Harness。
问题二：它是在设计任务如何持续推进吗？
比如触发条件、上下文装配、验证规则、状态记录、重试策略、停止条件、人工交接。
这是 Loop。
Agent 怎么行动 -> Harness 任务怎么收敛 -> Loop
写 Loop Spec，比写长 Prompt 更重要
以后你想让 AI 长期帮你做一件事，别一上来就写 2000 字 Prompt。
先确定下吗这些：
Loop Name 这个闭环叫什么？
Goal 最终要达成什么可验证结果？
Trigger 什么时候启动？
Context 每轮允许读取哪些材料？
Action 每轮最多做哪些动作？哪些动作禁止？
Verifier 通过标准是什么？由测试、规则、另一个 agent，还是人来验？
State 进度、失败原因、下一步写在哪里？
Budget 最多几轮？最多多久？最多多少成本？
Stop 什么情况停止？
Human Handoff 交给人时，要带哪些证据？
如果这张卡写不清楚，Prompt 写得再漂亮也只是一次请求。
如果这张卡写清楚了，Prompt 只是 Loop 里的一个可替换部件。
Loop Engineering 火起来，不是因为大家突然发现 循环 这个概念。
循环早就有。 验证早就有。 状态机早就有。 CI/CD 早就有。
真正变化的是：AI Agent 的 Harness 越来越强，它已经能进入真实环境行动，于是人的工作开始上移。
过去你问：
这句 Prompt 怎么写？
现在你要问：
这个目标怎么定义？ 上下文怎么装配？ 验证器怎么设计？ 状态写在哪里？ 失败后怎么重试？ 什么时候停止？ 什么情况交给人？ Prompt Engineering 训练的是表达。 Context Engineering 训练的是信息组织。 Harness Engineering 训练的是系统边界。 Loop Engineering 训练的是闭环设计。
所以别把 Loop Engineering 理解成“让 AI 自己无限跑”。
它是把人原本一轮轮接力、判断、纠偏、验收的工作，设计成一个可观察、可验证、可停止、可交接的系统。
你不是退出循环。 你是从循环里的操作者，变成循环外的设计者。
