The three Kimi brains. Only one fits your desk.

This is where every article about "running Kimi locally" gets it wrong, and where you'll save yourself a wasted weekend and possibly a wasted $4,000.
Moonshot publishes weights for models at wildly different scales. They are not interchangeable, and the flagship does not run on your hardware. Not "runs slowly" - does not run.
plaintext
MODEL                    TOTAL / ACTIVE   WEIGHTS ON DISK   LICENSE   RUNS AT HOME?
Kimi-Linear-48B-A3B      48B / 3B         ~28GB (Q4)        MIT       YES - one card
Kimi K2.7 Code           ~1T / 32B        325GB (2-bit)     modified  ONLY on a big box
Kimi K3                  2.8T             ~1.4TB (MXFP4)    modified  NO
Kimi K3 is not a home model. 2.8 trillion parameters. Native MXFP4 weights land around 1.4TB. Squeeze it to 2-bit and you're still near 1TB; push to aggressive sub-2-bit and you get 650–700GB of heavily degraded model. There is no consumer GPU in this conversation - not a 5090, not a 3090, not even a 96GB RTX PRO 6000. The realistic private deployments are four 512GB Mac Studio nodes over Thunderbolt 5 at roughly $40,000, or a dual-socket EPYC box with 1–1.5TB of DDR5 that will hand you single-digit tokens per second. Renting eight H100s is cheaper than both.
Kimi K2.7 Code is the ceiling for a serious home box. Around 1T parameters with 32B active, 325GB at 2-bit. That needs a machine with real memory - 512GB Mac Studio territory, or a big-RAM server with CPU offload. Possible. Not cheap, not fast.
Kimi-Linear-48B-A3B is the one you actually run. 48B total, only 3B active per token, and it's the interesting piece of engineering in Moonshot's lineup rather than just a shrunk-down flagship:
plaintext
Architecture      hybrid linear attention - Kimi Delta Attention (KDA)
                  3:1 KDA-to-global-MLA ratio
Context           1M tokens
KV cache          up to 75% smaller than full attention
Decoding          up to 6x faster at long context
License           MIT - no revenue clause, no attribution rule
Quantized builds  llama.cpp, Ollama, LM Studio, Jan
That KV cache number is the reason this works on a desk. Long context normally eats memory faster than the weights do - a 1M-token conversation in a conventional model blows past your VRAM long before the weights become the problem. KDA cuts the cache by three quarters, which is what lets a home box hold a real working context instead of a toy one.
And the license genuinely is MIT. No monthly-active-user threshold, no revenue clause, no attribution banner. Ship it in a product, sell the product, owe nobody anything.

The build. Four commands and one config file.

This is the entire setup. It takes about fifteen minutes, most of which is the model downloading.
bash
# 1 - the runtime
curl -fsSL https://ollama.com/install.sh | sh

# 2 - the brain (Q4 build, ~28GB)
ollama pull kimi-linear:48b-a3b-q4_K_M

# 3 - the body
curl -fsSL https://x.ai/cli/install.sh | bash

# 4 - confirm the runtime is serving on the OpenAI-compatible port
curl http://localhost:11434/v1/models
Now wire them together. grok-build reads ~/.grok/config.toml:
# ~/.grok/config.toml

[model.kimi-local]
model           = "kimi-linear:48b-a3b-q4_K_M"
base_url        = "http://localhost:11434/v1"
name            = "Kimi Linear 48B (local)"
api_backend     = "chat_completions"
context_window  = 262144

# keep a frontier fallback on the same install
[model.kimi-k3]
model           = "kimi-k3"
base_url        = "https://api.moonshot.ai/v1"
name            = "Kimi K3 (api)"
api_backend     = "chat_completions"
context_window  = 1048576
The /v1 on the end of base_url is not optional - grok-build speaks the OpenAI chat-completions shape, and Ollama only exposes that under /v1. Leave it off and you'll get a connection that opens and then does nothing, which is a genuinely annoying twenty minutes to debug.
Set context_window to what the model actually does at your quantization, not the headline number. Claiming 1M on a 32GB box means the agent will happily build a request your machine can't hold.
Then run it:
bash
grok models                              # list what's wired up
grok -p "explain this repo" -m kimi-local
grok                                     # full TUI
Inside the TUI, /model kimi-local switches brains mid-session, or Ctrl+M opens the picker. Same terminal, same workflow, same agent - the only thing that changed is which machine does the thinking.
Verify it's actually local. Watch the runtime log while you send a prompt:
bash
journalctl -u ollama -f          # linux
tail -f ~/.ollama/logs/server.log # macOS
If requests show up there, nothing left your machine. If they don't, you're still on the API and still paying.

The hybrid. Keep one metered key, not three subscriptions.

Nobody should run 100% local, and anyone telling you otherwise hasn't shipped anything hard. The move is to make the frontier metered instead of subscribed - you pay for the 20% you actually use rather than renting unlimited access you touch twice a week.
Wire both into the same agent and switch with one keystroke. From section 5 you already have kimi-k3 configured. Here's what that 20% actually costs:

A router keeps you honest about which is which:
python
# route.py - send it local unless it's genuinely hard
import os, requests

LOCAL = "http://localhost:11434/v1/chat/completions"
FRONTIER = "https://api.x.ai/v1/chat/completions"

HARD = ("architecture", "race condition", "why is prod",
        "design from scratch", "security review")

def ask(prompt: str, force_frontier: bool = False):
    hard = force_frontier or any(k in prompt.lower() for k in HARD)
    url, model, key = (
        (FRONTIER, "grok-4.6", os.environ["XAI_API_KEY"]) if hard
        else (LOCAL, "kimi-linear:48b-a3b-q4_K_M", "not-needed")
    )
    r = requests.post(
        url,
        headers={"Authorization": f"Bearer {key}"},
        json={"model": model, "messages": [{"role": "user", "content": prompt}]},
        timeout=600,
    )
    r.raise_for_status()
    return r.json()["choices"][0]["message"]["content"], ("frontier" if hard else "local")

if __name__ == "__main__":
    text, where = ask("write a pytest for utils.parse_date")
    print(f"[{where}] {text}")
Crude on purpose. Keyword routing catches most of it, and the force_frontier flag handles the rest. Log which branch fires for two weeks and you'll know your real split - mine settled at 83/17.

What neither of them actually gave away.
Both companies made a real gift and both kept the piece that matters to them. Worth naming, because it explains why this combination works at all.
xAI gave the harness, kept the model. grok-build is genuinely complete and genuinely Apache 2.0. But Grok 4.6's weights are not public and never have been - you get the body, you rent the brain. The
license is also read-only in practice
: you can fork, ship, and sell, but upstream doesn't take your patches. Fine for a user. Frustrating if you wanted a community around it.
Moonshot gave the model, kept the tooling. The weights are on Hugging Face and Kimi-Linear is real MIT. But K2.7 and K3 carry a modified license with a commercial threshold - cross roughly $20M in annual revenue running a model-as-a-service business on them and you need a separate agreement. And Moonshot ships no agent of their own that competes with what you're getting free from xAI.
Which is exactly why the combination works: each one open-sourced the half the other one was protecting. That is not coordination - it's two companies with opposite moats, and you get to stand in the gap.
Don't mistake either for charity. xAI wants the harness to be the default so their API is the default backend. Moonshot wants the weights everywhere so the paid tiers get considered. Both bets are rational. Both leave a working free stack on the table.
